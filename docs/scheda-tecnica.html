Ogni module-*.js è uno script indipendente (IIFE) che legge/scrive lo stato condiviso su window.GMA3 e inserisce il proprio pannello nel DOM. Il server conosce solo le cue; tutto il resto vive lato client.

4. Data flow

Fader (drag/click)

evento puntatore → calcolo percentuale → state.faders[i] aggiornato → repaint DOM + Stage View

Cue

form submit → POST /api/cue/create → validazione server → 201 + cue → GET /api/cue/list → render griglia

Scena

Store Scene → localStorage.setItem → render lista
GO → localStorage.getItem → state.faders = scena → repaint

Automazione

setInterval(N secondi) → scena successiva → applica fader → sincronizza layer Catalyst

7. Limiti e scalabilità

Uso previsto: demo e training interno. Non progettato per produzione multi-utente.
  • Le cue vivono in un singolo processo Node — con più repliche del server (es. dietro un load balancer) ogni istanza avrebbe cue diverse.
  • Nessuna autenticazione: chiunque raggiunga il server può creare/eliminare cue.
  • Nessun database: al riavvio del server tutte le cue spariscono.
  • Scene/patch/design sono per-browser: due postazioni diverse non condividono lo stato.

Percorso per renderlo scalabile (vedi anche docs/TECHNICAL.md):

  1. Sostituire l'array cue in memoria con un database (Postgres, Redis, ecc.).
  2. Spostare scene/patch/design lato server, associate a un utente/sessione.
  3. Aggiungere autenticazione se multi-utente.
  4. Per deploy serverless (Vercel, ecc.): serve uno store esterno, il processo Node persistente attuale non è compatibile con funzioni stateless.

8. Requisiti

  • Node.js (qualsiasi versione recente con supporto Express 4)
  • Browser moderno con supporto Canvas 2D, localStorage, ES6
  • Nessuna GPU, nessun plugin, nessuna installazione lato client
